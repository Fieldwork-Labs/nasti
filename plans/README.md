## Architectural outcome

NASTI will have three deliberately separate forms of state:

1. **Offline identity**: a minimal, persisted snapshot used to unlock the local
   application for at least 30 days after a successful login or token refresh.
   It is never a bearer credential.
2. **Request credentials**: a bounded, request-time acquisition of a real
   Supabase session. Uploads do not start without it, and the acquired token is
   bound to the exact request.
3. **Durable work queues**: row and media work survives loss of connectivity,
   refresh failure, process restart, and individual permanent failures.
   Permanent failures are preserved locally before a queue advances.

This follows the useful separation in Fieldbook's
`docs/offline-auth-startup-handoff.md` and
`docs/upload-authentication-architecture.md`, while avoiding its synthetic
offline `Session`: NASTI should represent offline identity as its own type so
TypeScript prevents it from being passed to a network adapter.

  and live network credentials.

  adapter.
- Plan 004 exposes the failure records and queue state introduced or hardened
  by Plans 002 and 003.

## Findings considered and rejected

- Using `navigator.onLine` as proof that authentication will complete: rejected
  because captive portals and poor reception can leave requests pending while
  the browser reports online.
- Persisting or reusing an expired access token for uploads: rejected because
  it conflates offline identity with network authorization.
- Completing ambiguous `42501` failures after a fixed retry count: rejected
  because authentication outages can outlast any arbitrary budget and valid
  data would be discarded.
- Keeping React Query mutations as the media queue: rejected because mutation
  variables contain `File` objects and do not provide the durable,
  restart-safe byte lifecycle this requirement needs.
