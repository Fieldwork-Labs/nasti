# Plan: Transfer (ownership transfer of seed bags between organisations)

Status: approved · 2026-11-18 · second-review defaults confirmed · web only
(`apps/web`) + Supabase. [Implementation handoff](../handoffs/2026-11-18-1215-transfer-implementation.md)

## Goal

An organisation can permanently give seed bags (or a weighed part of a bag) to
another organisation. It works like send-for-testing, except ownership moves
and nothing comes back. The recipient receives a new batch of its own. It sees
the species, the collection code, the latest result of each test type with
quality stats, and storage dates. It sees nothing else of the sender's data.

## Decisions this plan builds on

| Topic | Decision |
| --- | --- |
| Recipient side | A **new batch** in the recipient org, with a provenance link to the source |
| Discovery | **Opt-in directory**: `organisation.accepts_transfers`. Any org type can opt in, testing providers included |
| Link | First transfer to an org sends a **link request**, which the recipient must accept. Once linked, transfers are **immediate** |
| Opt-out | Stops new incoming sends, closes pending incoming requests and releases their bags. Accepted incoming links are dormant and reactivate on opt-in |
| While a link is pending | Selected bags are **reserved and locked**. They move on accept and unlock on decline or cancel |
| Quantity | Whole bag, or a weight split off first (as testing does) |
| Tests shown | **One latest result per type or quality subtype across captured hops**, credited to the performing org and dated. Omit source-batch seed-count estimates |
| Test freshness | **Captured at completion.** Later tests by the sender never reach the recipient |
| Storage shown | **Dates and durations captured at completion**, cut off when the transferred seed left each ancestor bag. Storage conditions are a future feature |
| Sender keeps | A history record only ("transferred to X, N g, date") |
| Who can send | Members with the **`inventory`** permission (Admins always) |
| Excluded | Bags **out for testing**. Uncleaned and previously-received bags are allowed, so onward transfer works |
| New batch code | Displays the **source collection code** |
| Cleaning received seed | Use the recipient's species and the source collection code. Cleaned output keeps that source code for onward transfer and starts a fresh test history |
| Collection facts shared | The recipient gets the source collection's **IBRA region, species and collection year**. These travel with the seed (captured at completion, carried through cleaning and onward transfer). No other collection details are shared (location, collectors, notes, dates beyond the year) |
| Mixing or combining received seed | **Deferred, so not in v1.** The UI disables these actions for received batches and explains why. The captured IBRA region (above) makes a later decision possible without another schema change |
| Notify | In-app, plus **email** to recipient Admins (Mailgun, as in `create_link_request`) |

## How it maps onto what exists

- `seed_transfer_event` / `seed_transfer_item` (`20260911000001_inventory_foundation.sql`)
  are already the movement ledger. Transfer adds one event kind. Three
  constraints and validators reject it today and must change (1.2).
- `fn_assign_bags_for_testing` (`20260911000004_testing_work_and_custody.sql:149`)
  is the template. It validates, locks bags then batches, can split a sample off,
  closes storage, writes the event, and changes `held_by_org_id`. The new RPC
  follows the same structure and the same error-code contract.
- `organisation_link` / `organisation_link_request` are testing-only. The
  `validate_testing_provider_link` trigger requires `is_testing_provider`, and
  their RLS lets Admins write them directly (`20260911000005_…:2026`).
- `batches.species_id` already exists for batches with no collection (combined
  batches). A transferred batch uses that too: `collection_id` is NULL and
  `species_id` is set.
- `batches.code` has **no uniqueness constraint** (only `collection.code` is
  unique per org). Repeat receipts from one collection may share a code; they
  are told apart by batch id and the "Received from X" badge.
- **Species rows are org-scoped** (`species.organisation_id`, and `species_select`
  is org-or-holder). The recipient needs a species row of its own (see 2.4).
- Whole-batch merge and mix consume source batches through `batch_merges`.
  The sources can still have positive `sub_batch_current_weight` after that.
  Reservation and availability checks must cover this path (2.8).
- **Active inventory** is defined by `active_sub_batches`
  (`20260911000003_…:2906`): current weight > 0, held by the caller's org,
  parent batch not a `batch_merges` source, and bag not a `batch_cleaning`
  input. Send (2.3) and accept (2.5) use these same rules, evaluated under the
  bag lock and without depending on the caller's org.
- **Cleaning today.** The web calls only `fn_clean_batch` (`hooks/useCleanBatch.ts`),
  which handles a collectionless batch (species and code from the batch) but
  refuses a batch that has bags. The bag-level `fn_clean_sub_batch_without_lineage`
  (`20260911000003_…`) raises "Parent batch has no collection". A received
  batch always has one bag, so neither path cleans it today (2.10).
- **Mix and combine** (`fn_mix_batches`, `fn_combine_batches`) join
  `collection` to check one IBRA region. They reject received batches, which
  have no collection.
- **Direct storage writes from the web.** `useUpdateStorageRecord`
  (`hooks/useBatchStorage.ts:376`) updates `batch_storage` directly. 2.8
  replaces it with an RPC.
- Edge functions that verify JWTs themselves have a `verify_jwt = false` entry
  in `supabase/config.toml` (as `assign_batches_for_testing` does).
- The bag basket (`store/bagBasketStore.ts`) and `send-for-testing.tsx` (weights via
  `lib/sendingWeight.ts`) are the UI template.

## 1. Schema (two forward migrations)

Write migrations only. Don't apply them, and don't regenerate types: the user
applies and regenerates. Hand-edit `packages/common/types/database.ts` only if
the code won't compile without it, and say so.

PostgreSQL won't let a value added by `ALTER TYPE … ADD VALUE` be used until
its transaction commits. Split the work:

- **Migration A, enums only.**
- **Migration B, everything else:** constraints, tables, triggers, policies and
  functions that use the new values.

### 1.1 Enums (migration A)

- `seed_transfer_event_kind` gets `'ownership_transfer'`.
- `batch_weight_adjustment_kind` gets `'transfer_out'`.
- `sub_batch_lineage_operation_kind` gets `'transfer'`.
- New `organisation_link_kind` enum: `('testing', 'transfer')`.

### 1.2 Ledger constraints and validators (migration B)

- **`batch_weight_adjustment_reference_shape`**: add a `transfer_out` arm that
  requires `transfer_item_id` and nothing else, like `variance`.
- **`seed_transfer_event_reference_shape`**: add `ownership_transfer` to the
  `testing_dispatch` / `return` arm (no reversal or correction reference).
  Today it rejects the new kind outright.
- **`validate_sub_batch_lineage_edge`**: it raises "Lineage cannot cross seed
  owners". Allow a cross-owner edge only when `operation_kind = 'transfer'` and
  a **completed-in-this-transaction** mapping exists:
  - `seed_transfer_item.id = NEW.operation_id`, its `sub_batch_id` is the
    source bag, and its event is `ownership_transfer`;
  - an `ownership_transfer_item` with that `seed_transfer_item_id`, whose
    `received_sub_batch_id` is the derived bag;
  - the derived bag's batch is owned by the transfer's recipient.

  Keep the owner check, the cycle checks and the per-kind rules for `split`,
  `merge` and `cleaning` exactly as they are.

### 1.3 Directory flag

`organisation.accepts_transfers boolean NOT NULL DEFAULT false`, with a partial
index. Only Admins may change it through the RPC in 2.9. Protect the column
from direct client writes so the toggle and reservation releases are atomic.
`organisation_update` lets an Admin update the whole row today, so use the
same guard as 1.6: an invoker trigger rejecting a change to
`accepts_transfers` from the `authenticated` role. The settings form must
stop sending the field in its ordinary update.

### 1.4 Generalise links

- Add `kind organisation_link_kind NOT NULL DEFAULT 'testing'` to both
  `organisation_link` and `organisation_link_request`.
- Change unique `organisation_link_unique` to `(requesting_org_id, provider_org_id, kind)`.
- Add `declined_at`, `declined_by` and `cancelled_at` to `organisation_link_request`.
  Today a request can only be accepted.
- **One open transfer request per directional pair**: a partial unique index on
  `organisation_link_request (requesting_org_id, provider_org_id)`
  `WHERE kind = 'transfer' AND accepted_at IS NULL AND declined_at IS NULL AND cancelled_at IS NULL`.
  Legacy testing requests can contain duplicate pending rows and stay outside the index.
- **Validate trigger**: checks `is_testing_provider` for `testing` and
  `accepts_transfers` for `transfer`. Both triggers already exist
  (`20260911000005_…:2619`) but fire only on `INSERT OR UPDATE OF provider_org_id`.
  Widen them to `UPDATE OF provider_org_id, requesting_org_id, kind`.
- **Recipient approval is enforced in SQL, not only in the UI.** Today a
  requester Admin can `UPDATE` a link row, so changing `kind` could mint a
  transfer link with no approval. Rewrite the insert, update and delete
  policies on both link tables so they cover `kind = 'testing'` only: in
  `USING` (the old row) and in `WITH CHECK` (the new row). Transfer rows are
  written only by the RPCs in section 2.
- **Organisation visibility.** `organisation_select` exposes a requesting org's
  full row (contact fields included) to members of a linked provider. Scope
  that `EXISTS` clause to `ol.kind = 'testing'`. Transfer partners see each
  other only through the RPCs, which return names alone.
- Links are **directional**: A→B lets A send to B. B sending to A needs its
  own link.
- Existing testing code must filter `kind = 'testing'`: `is_linked_testing_provider`,
  `fn_assign_bags_for_testing`, the `create_link_request` and `accept_link_request`
  edge functions (so neither can create or accept a transfer request), and
  `hooks/useTestingOrgs.ts`.

### 1.5 Transfers and reservations

- **`ownership_transfer`**: `id`, `sender_org_id`, `recipient_org_id`,
  `status` (`pending_link` | `completed` | `cancelled` | `declined`),
  `link_request_id` (nullable), `transfer_event_id` (nullable, set on completion),
  `notes`, `created_by`, `created_at`, `resolved_at`, `resolved_by`.
  Store a client-generated `request_id` and a normalized input or fingerprint
  for replay checks. Enforce uniqueness on `(sender_org_id, request_id)`.
- **`ownership_transfer_item`**: `id`, `transfer_id`, `sub_batch_id` (the bag
  that will move, after any split), `weight_grams` at send time, and
  `seed_transfer_item_id` / `received_batch_id` / `received_sub_batch_id`
  (set on completion).
- **`sub_batch_reservation`**: `sub_batch_id uuid PRIMARY KEY`,
  `transfer_id uuid NOT NULL`, `created_at`. One row is one active reservation.
  The primary key makes a second reservation of the same bag impossible.
  Rows are inserted when a pending transfer is created and deleted, in the
  same transaction, when it completes, is declined or is cancelled. (The
  original partial index on `ownership_transfer_item` couldn't work: an index
  predicate can't read the parent transfer's status.)
- `is_bag_reserved(sub_batch_id)` is an `EXISTS` on this table, for the UI and
  the guards in 2.8.

### 1.6 Provenance on the received batch

- Add `batches.received_transfer_item_id uuid`, referencing `seed_transfer_item`,
  and `batches.source_collection_code text`. The transfer pointer identifies
  the exact received batch. The source code is also carried into batches
  produced by cleaning received seed (2.10).
- Also add `batches.source_ibra_code text` (the code from
  `get_ibra_code_from_location(collection.location)`) and
  `batches.source_collection_year smallint` (from `collection.collected_on`).
  They are captured and carried exactly like `source_collection_code`. The
  region name is resolved from `ibra_regions` at read time.
- **Protect these columns from clients.** `authenticated` holds a table-level
  `UPDATE` grant on `batches`, and `batches_update` lets a custodian update
  its own rows. Restrict writes to these columns to the authorised database
  paths for completion and cleaning. Use column grants or an invoker trigger
  that checks the effective database role. Keep the fields immutable after
  insertion. The provenance RPCs validate the pointer independently (2.7).
- **Captured test results:**
  `ownership_transfer_test_snapshot` with `ownership_transfer_item_id`,
  `hop` (0 for this transfer's source batch, n for earlier hops),
  `source_test_id`, `type`, `quality_test_type` (nullable), `statistics`,
  `result` (projected, see 2.7), `tested_at`, `performed_by_organisation_id`.
  Written only by 2.4.
- **Captured storage periods:** `ownership_transfer_storage_snapshot`, keyed
  to the same transfer item. Store start, bounded end and duration as in 2.7.
  The snapshot holds dates and durations only and is written by 2.4.

### 1.7 RLS and grants

- Members of the sender or recipient org can select `ownership_transfer` and
  its items. Exclude the replay input or fingerprint from the client projection.
  `sub_batch_reservation` and both snapshot tables are read through RPCs.
- No direct writes on any new table. Everything goes through RPCs.
- The existing `seed_transfer_*` select policies already cover both parties.
- Function grants: functions start out executable by `PUBLIC`, `anon` and
  `authenticated` (`20260911000005_…:2713`). Revoke `EXECUTE` on
  `fn_complete_ownership_transfer` and `fn_close_storage_for_transfer` from
  all three, as the file already does for the other internal steps.

## 2. Database functions

Transfer RPCs and internal completion helpers are `SECURITY DEFINER` with
`search_path ''`. They resolve the
caller's org the same way the testing functions do, and raise the same
SQLSTATEs (`28000`, `42501`, `P0002`, `55000`, `22023`) so the edge-wrapper
mapping can be reused.

### 2.1 Locking and state rules (all lifecycle functions)

Send (2.3), respond (2.5), cancel (2.6) and the setting change (2.9) follow one order.

1. **Recipient organisation row.** Take `FOR SHARE` for the directional pair's
   lifecycle calls and `FOR NO KEY UPDATE` for the settings RPC. This serialises
   opt-out with incoming sends and accepts while allowing independent senders
   to operate concurrently. Read the opt-in flag under this lock.
2. **Pair lock.** Take `pg_advisory_xact_lock` on a key derived from
   `(sender_org_id, recipient_org_id, 'transfer')` before reading mutable request,
   link or transfer state. When closing multiple pairs, lock them in stable order.
3. **Bags, then batches**, `FOR UPDATE`, each in ascending id order, as
   `fn_assign_bags_for_testing` does (`20260911000004_…:309`).
4. **Re-check state under the locks.** Confirm the request and transfer are
   still non-terminal before writing a ledger event or releasing a
   reservation. A transfer already `completed`, `declined` or `cancelled` is
   a no-op or a `55000`, never a second completion.

### 2.2 `fn_transfer_directory()`

Returns `id, name, is_linked, has_pending_request` for orgs with
`accepts_transfers` other than the caller's own. Names only, no contact fields.

Don't widen `organisation` RLS. The current `OR is_testing_provider` clause
already exposes contact fields for testing orgs, and the directory needs only
names.

### 2.3 `fn_send_bags_for_transfer(p_recipient_org_id uuid, p_bags jsonb, p_notes text, p_request_id uuid)`

`p_bags` has the same shape as testing: `sub_batch_id` and optional
`sample_weight_grams`. There is no container field; the sender's containers
mean nothing to the recipient.

1. **Gate.** Require `has_org_permission('inventory')`, a request ID and a
   recipient different from the caller's org.
2. **Lock the recipient and pair, then check for replay.** Match on the sender
   org and request ID. Compare normalized recipient, bag IDs, quantities and notes.
   On a match, return the existing transfer with `replayed = true` before
   checking current bag eligibility or recipient opt-in. Reject reuse of the
   key with a different payload (`22023`). For a new intent, require the
   recipient to exist and be opted in.
3. **Lock bags and batches as in 2.1 and validate every bag before writing.**
   Each bag must be:
   - owned and held by the caller,
   - free of an active testing assignment,
   - not in `sub_batch_reservation`,
   - active inventory as defined above: current weight > 0, parent batch not
     consumed by a merge, mix or combine, and bag not a cleaning input.

   A sample weight must be less than the current weight. Error messages follow
   `fn_assign_bags_for_testing`.
4. **Claim the request ID** by inserting the `pending_link` transfer before any
   split or reservation. Resolve a unique-key conflict against the stored
   payload using step 2. Split each bag that has a sample weight using
   `fn_split_sub_batch` with the note "Portion sent for transfer". The child
   bag is the one that moves. Record the items against the claimed transfer.
5. **Branch on link state** (read under the pair lock).
   - **A `transfer` link exists:** call `fn_complete_ownership_transfer` (2.4)
     in the same transaction, which sets `completed`.
   - **No link:** reuse the one open transfer request for the pair, or create
     one. Attach the transfer to it and create one `sub_batch_reservation`
     row per bag.
6. Return the transfer row, whether a link request was created and whether this
   was a replay. Only the first successful send can trigger email.

### 2.4 `fn_complete_ownership_transfer(p_transfer_id uuid)`

Internal only (1.7). Called from 2.3 and 2.5, which have already taken the
locks of 2.1 and checked that the transfer is `pending_link`.

It runs under either party's `auth.uid()`: the sender on an immediate send, the
recipient Admin on accept. So it must not depend on caller-org checks in the
public RPCs it would otherwise reuse. Insert protected provenance columns
through the authorised database path in 1.6.

1. **Release the reservations** for this transfer (`DELETE FROM
   sub_batch_reservation`) first, so the guards in 2.8 don't block the
   completion's own writes.
2. Insert one `seed_transfer_event` (`ownership_transfer`, sender → recipient).
3. For each item, in sub-batch id order:
   1. **Close storage** with `fn_close_storage_for_transfer(sub_batch_id, now,
      'Transferred to <org>')`. This is a new internal function. It sets
      `moved_out_at` on the open storage row and is a no-op when the bag isn't
      stored. Don't call `fn_set_sub_batch_storage`: it requires the caller to
      be the bag's current holder, which fails for a recipient accepting, and
      it raises on an unstored bag.
   2. Insert a `seed_transfer_item` for the source bag with its current
      weight and `owner_org_id` = sender.
   3. **Resolve the recipient's species.** Match on `ala_guid` first, then on a
      case-insensitive `name`. Otherwise insert a species row into the
      recipient org, copying `name`, `ala_guid` and `indigenous_name`. Get the
      source species from the collection, or from `batches.species_id`.
   4. **Create the batch:**
      - `organisation_id` = recipient, `collection_id` NULL, `species_id` from the previous step;
      - `source_collection_code`: the source collection's `code`, or the source
        batch's `source_collection_code` for an onward transfer;
      - `source_ibra_code` and `source_collection_year`: from the source
        collection, or copied from the source batch for an onward transfer
        or a cleaned receipt;
      - `code` = `source_collection_code` (no suffix: codes aren't unique);
      - `received_transfer_item_id` set.

      Don't route this through `fn_create_origin_batch_for_collection`; that
      one is collection-triggered.
   5. Create the received bag: weight = moved weight, `held_by_org_id` = recipient,
      `container_id` NULL.
   6. Write a `transfer_out` weight adjustment of minus the moved weight on the
      source bag. The bag stays in the sender's batch at zero, so
      `active_sub_batches` drops it.
   7. **Record the mapping** on the `ownership_transfer_item`:
      `seed_transfer_item_id`, `received_batch_id`, `received_sub_batch_id`.
   8. Insert `sub_batch_lineage` (source bag → received bag, `'transfer'`,
      `operation_id` = seed transfer item id). It comes after step 7 because
      the validator (1.2) checks that mapping.
   9. **Capture tests and storage** as defined in 2.7. For an onward transfer,
      include authorised snapshots from previous receipts. Read those snapshots
      for earlier hops.
4. Set the transfer to `completed` with `transfer_event_id` and `resolved_at`.
   All of this is one transaction: any failure rolls back the whole completion.

### 2.5 `fn_respond_transfer_link_request(p_request_id uuid, p_accept boolean)`

- **Caller:** an Admin of the recipient org. The plan picks Admin because a
  link is a standing relationship (see Resolved question 2).
- Take the locks of 2.1 for the request's pair and every bag reserved by its
  pending transfers. Re-check that the request is still open.
- **Accept:** check the recipient is still opted in under the organisation row
  lock. Create the `transfer` link, mark the request accepted, then
  complete every `pending_link` transfer attached to the request with 2.4.
  Re-validate the reservation and every eligibility rule in 2.3. A bag that
  fails cancels its transfer and releases its
  reservations instead of failing the accept.
- **Decline:** mark the request declined, set its transfers to `declined`, and
  delete their reservations.

### 2.6 `fn_cancel_ownership_transfer(p_transfer_id uuid)`

The sender (inventory permission) can cancel a transfer only while it is
`pending_link`. Take the locks of 2.1, re-check status, set `cancelled`, and
delete its reservations. If no other pending transfers remain on the request,
the request is cancelled too, under the same pair lock, so a concurrent send
either attaches before the cancel or opens a new request after it.

**A split-off portion stays as its own bag after cancel or decline.** It is not
re-merged automatically; the user can merge it back.

### 2.7 Read functions for the recipient

**Authorising every hop.** Each read function checks that the caller's org
owns `p_batch_id` and that a completed transfer's item records this exact
batch as its received output. Match the ledger item against the batch pointer
and check the received bag, source bag and parties against the saved mapping.
For earlier hops, verify each mapping and that its recipient owned the output
that feeds the next hop. Only the starting batch must belong to the caller.

- **`fn_received_batch_provenance(p_batch_id)`.** Returns:
  - sender org name and transfer date, for each hop in the chain;
  - species name;
  - `source_collection_code`;
  - `source_ibra_code`, the IBRA region name, and `source_collection_year`;
  - **one latest test per type or quality subtype across all valid captured
    hops**: `type`, `quality_test_type`, `statistics`,
    `tested_at`, performing org name, and a projected `result`.
- **Result projection.** Return named fields only, never the raw `result`
  jsonb: quality results include free-text `notes`. For quality tests that is
  `test_type`, `psu_grams`, `inert_seed_weight_grams`,
  `other_species_seeds_grams`, `relative_humidity_percent` and `repeats`
  (`packages/common/types/index.ts:181`). Reconstruct each repeat from its
  allowed numeric fields and project the statistics too. Exclude `plsCount`
  and `psuCount`, which are estimates for the sender's full tested batch.
  Use an explicit projection for other test types.
- **Test scope.** Today the owner sees a batch's tests by `batch_id`
  (`useBatchTests`), and every bag of a batch shares them. To match that, take
  tests recorded against the **source batch**. For onward transfers, include
  each earlier hop's source batch. Don't go further: cleaning produces a new
  batch, which already drops pre-cleaning tests.
- **Ranking.** At capture, filter source tests by `deleted_at IS NULL`. Keep
  its latest result per `type` or quality `result->>'test_type'` at hop 0 and
  carry the validated prior snapshots with incremented hop numbers. Rank the
  captured candidates across hops using `tested_at DESC NULLS LAST` and
  `source_test_id DESC` as the stable tie-breaker. Return one winner per
  partition with its original date and performing organisation. Later edits,
  deletions and new tests on a sender's batch leave the snapshot intact.
- **`fn_received_batch_storage_history(p_batch_id)`.** Return captured dates
  and durations only. At completion, walk the source bag and its split and
  merge ancestors within the sender's inventory. For each ancestor, cap the
  end of each period at the edge where the transferred seed left that bag.
  Cap periods on the source bag at transfer completion. Exclude periods that
  start at or after the cutoff, cap open or longer periods at the cutoff,
  and deduplicate repeated paths to the same period. At an earlier transfer
  edge, carry forward that validated receipt's captured periods. Earlier
  organisations' live storage records are outside the snapshot read path.

### 2.8 Locking reserved bags

A reserved bag must not be split, merged, cleaned, mixed or combined. It also
must not be tested, sent for testing, have its storage changed (added, moved
or removed), or be put in another transfer.

Use a shared reservation check that raises `55000` ("Bag is reserved for a
pending transfer"). Apply it at the affected write points, including updates
that only close a storage period. Audit the relevant insert, update and delete
paths. The bag-level guard covers these tables.
- `batch_weight_adjustments` (`sub_batch_id`)
- `sub_batch_lineage` (`source_sub_batch_id`)
- `tests` (`sub_batch_id`)
- `batch_testing_assignment` (`sub_batch_id`)
- `batch_storage` (`sub_batch_id`), insert and update
- `sub_batches` (`id`), update, for `container_id`, `held_by_org_id` and
  `batch_id` changes

**Whole-batch operations.** `fn_merge_batches` and `fn_mix_batches` consume a
source via `batch_merges` without adjusting its bags. Lock and check every
affected source bag before reading available weight or consuming the batch.
Apply the same rule to any whole-batch or direct-write path that consumes or
reassigns those bags, and cover deletion of a reserved bag or its parent.
Review the normal and direct write paths in the PR.

**Race safety.** Acquire the bag lock before reading its eligibility or weight
in any mutation, including `fn_clean_sub_batch`. The write-time guard is a
backstop. Move client `batch_storage` edits, including notes and location,
through a bag-first RPC and remove the direct authenticated update path.
Take the bag lock before the storage row in all storage writers. PostgreSQL
locks the storage row before running a row-level update trigger, so trying
to take the bag lock there would reverse the order used by completion.

The completion path needs no exemption: 2.4 deletes the reservation before its
own writes.

### 2.9 Set incoming transfer availability

An Admin of the organisation calls `fn_set_accepts_transfers(p_accepts boolean)`.
Use the organisation row, pair and bag lock order in 2.1. On opt-out, set the
flag to false, mark all open incoming `transfer` requests and their pending
transfers as cancelled, and delete their reservations in the same transaction.
Keep already accepted incoming links. On opt-in, set the flag to true so those
links permit new immediate sends. Cancelled requests and transfers stay closed.

### 2.10 Clean received bags

A received batch has a bag, so it must be cleaned through the bag-level path.

- **SQL.** Give `fn_clean_sub_batch_without_lineage` the collectionless branch
  `fn_clean_batch` already has (`20260930000002_…:222`): the base code is the
  parent batch's `code`, the output species is the parent's `species_id`, and
  output numbering is scoped to the org's collectionless batches. Copy the
  parent's `source_collection_code`, `source_ibra_code` and
  `source_collection_year` onto each output. Do the same copy in
  `fn_clean_batch` for collectionless inputs that carry one. Both writes go
  through the protected-column path in 1.6.
- **Outputs.** Each output keeps its own cleaning code and ordinary cleaning
  lineage. It starts a fresh test history and has no `received_transfer_item_id`,
  which belongs to the original receipt. A later transfer captures tests from
  the cleaned batch and excludes pre-cleaning snapshots.
- **Web.** The cleaning form calls `fn_clean_batch` only. When the input batch
  has bags, call `fn_clean_sub_batch` on its bag instead (a new
  `useCleanSubBatch` hook). Check the form doesn't read collection fields
  that a received batch lacks.

## 3. Edge functions (`supabase/functions/`)

These are thin transport wrappers like `assign_batches_for_testing`. All rules
live in SQL. Copy its `STATUS_BY_PG_CODE` map.

- **`send_bags_for_transfer`**: calls 2.3. Then it emails the recipient's Admins
  through Mailgun on a first successful send, reusing the block in
  `create_link_request/index.ts:190`. Skip email for `replayed = true`.
  - after a completed transfer: "<Sender> transferred N bags (species, collection codes) to you";
  - after a new link request: "<Sender> wants to transfer seed to you. Review the request."

  An email failure is logged and doesn't fail the request. Factor the Mailgun
  call into `_shared/` if it is copied a third time.
- **`respond_transfer_link_request`**: calls 2.5. On accept, sends the arrival
  email to the recipient's Admins, and a "request accepted" email to the user
  who sent the request.
- Cancel needs no email. The client calls 2.6 through `supabase.rpc`.
- `create_link_request` and `accept_link_request` filter `kind = 'testing'`
  (1.4). They must refuse transfer requests.
- Add `[functions.send_bags_for_transfer]` and
  `[functions.respond_transfer_link_request]` with `verify_jwt = false` to

## 5. Tests

- **SQL** (`supabase/tests/`, beside `seed_transfer_foundation.sql` and
  `sub_batch_testing_assignments.sql`), new `ownership_transfer.sql`:
  - **Immediate transfer:** the whole bag and the split portion both move. The
    source bag reaches zero, dropping by exactly the moved weight. The new
    batch has the recipient's species and the collection code. Ledger,
    mapping and lineage rows are written.
  - **Accept by the recipient Admin:** a stored whole bag (storage closes), an
    unstored bag, and a split portion. The recipient sees one new bag each,
    with its lineage edge.
  - **Pending:** the reservation blocks split, merge, clean, test, testing-send,
    a second transfer, storage edits and whole-batch merge and mix. Accept
    completes the transfer. Decline and cancel release it. Check that storage
    edits work again through the RPC and direct client updates are denied.
  - **Send replay:** submit a 30 g partial send twice on a 100 g bag with the
    same key. Assert one transfer and one split, with 70 g remaining on the
    source. Check key reuse with changed input and concurrent duplicate calls.
    In the wrapper, check that a replay sends no extra notification.
  - **Opt-out:** close pending requests from multiple senders, release every
    reservation and reject new incoming sends. Verify re-enabling restores
    previously accepted links without reopening cancelled requests.
  - **Concurrency** (two sessions, e.g. `dblink` or a scripted pair of `psql`
    sessions; record which ran): simultaneous first sends to one recipient;
    send versus accept, cancel or opt-out; opt-out versus accept; storage
    edit and whole-batch merge or mix versus acceptance. Assert at most one
    open transfer request per pair, no pending transfer attached to a
    resolved request, no orphaned reservation and conserved weight. Verify
    the duplicate send case also produces one completion.
  - **Rejections:** a bag out for testing, no inventory permission, a recipient
    not opted in, a bag the caller doesn't hold.
  - **Link isolation:** a sender Admin can't insert a transfer link, or update
    a testing link's `kind`, requester or provider into one. A transfer link
    doesn't expose the sender's `organisation` row to the recipient.
    `accept_link_request` can't accept a transfer request. The migration's
    transfer-only unique index allows pre-existing duplicate testing requests.
  - **Internal helpers:** `authenticated` can't execute
    `fn_complete_ownership_transfer` or `fn_close_storage_for_transfer`.
  - **Forged provenance:** setting `received_transfer_item_id` or
    `source_collection_code` directly fails, and a batch pointing at another
    org's transfer item returns nothing from the 2.7 RPCs.
  - **Test selection:** soft-deleted tests are skipped, equal timestamps
    resolve deterministically, each quality subtype gets its own latest row,
    and projected results and statistics exclude notes, unknown nested fields
    and source-batch count estimates. Edits, deletions and new tests after
    completion leave the recipient's snapshot intact.
  - **Storage snapshot:** transfer a portion of a stored bag, then move the
    original. The recipient's ancestor period ends at the split and stays
    the same after the move. Cover merge ancestry deduplication and onward
    use of an earlier receipt's snapshot.
  - **Onward transfer:** A→B→C keeps the collection code. When A and B have
    results for the same subtype, C gets only the latest captured result
    with its performing org and date. Also retain a subtype unique to A.
  - **Cleaning and onward transfer:** B can clean an uncleaned receipt through
    `fn_clean_sub_batch` and send it to C. Outputs carry B's species, numbered
    codes and the source collection code. C gets the original collection code
    and test results from the cleaned batch, with pre-cleaning snapshots
    excluded. Existing collection-backed and combined-batch cleaning still
    pass.
  - **Mix and combine:** both reject a received batch with their existing
    error and change nothing.
  - **Settings guard:** a direct `organisation` update of `accepts_transfers`
    fails; other Admin edits to the row still work.
  - **Visibility:** the recipient can't read the sender's collection, storage
    locations, contact details or other bags. The sender can't read the
    received batch.
  - **Testing regressions:** testing links still work and ignore transfer
    links; the existing SQL test files still pass.
- **Web** (Vitest, `lib/__tests__/`): cover any pure helpers extracted from the
  transfer page. Verify request ID reuse on retry and opt-out copy in the UI,
  the cleaning-path choice (batch versus bag), and that mix and combine are
  disabled for received batches.

## Resolved questions (defaults confirmed 2026-11-18)

1. **Test scope:** the source batch's tests, which matches how owners see
   tests today, rather than per-bag lineage. Every bag of a batch shares its
   tests, so this is the same as "the bag's lineage" in practice.
2. **Who accepts a link request:** the recipient's Admins.
3. **Who opts in to the directory:** Admins only (default).
4. **Links are directional:** each direction needs its own accepted request (default).
5. **Leftover split portion** after cancel or decline: stays a separate bag (default).
6. **Recipient species:** auto-created when there's no `ala_guid` or name
   match. Duplicates are possible if names differ slightly.
7. **Batch-level reads:** `active_batches` and similar views should show
   received batches with no special case, because `collection_id` is NULL and
   `species_id` is set, as for combined batches. Check the collection-joined
   columns (IBRA, collected date) don't break.
8. **Batch code uniqueness:** none exists, so received batches reuse the
   source collection code without a suffix.
9. **Test freshness:** results are captured at completion. A live read would
   also show tests the sender records later on seed it kept from the source
   batch, which the recipient never received. 1.6 adds the snapshot table,
   2.4 step 9 fills it, and 2.7 reads only from it. The recipient's own later
   tests appear through the normal `useBatchTests` path on its batch.
10. **Opt-out:** cancel pending incoming requests and transfers, and release
    their reservations. Opting back in reactivates accepted incoming links.
11. **Storage history:** capture dates and durations at completion. Cut off
    each ancestor's periods when the transferred seed left that bag.
12. **Onward test display:** one latest captured result per type or quality
    subtype across valid hops, with the original date and performing org.
    Omit source-batch seed-count estimates.
13. **Cleaning:** a received bag can be cleaned using the recipient's local
    species and source collection code. The cleaned output keeps that code
    for onward transfer and starts a fresh test history.
14. **Mix and combine of received seed:** deferred (user, 2026-11-18), so
    disabled in v1. The IBRA region, species and collection year are shared
    with the new owner and captured on the received batch, so a later
    decision needs no schema change. Other collection details stay private.

## Out of scope

- Removing a transfer link. Direct deletes now cover testing links only, so
  unlinking a transfer partner needs its own RPC later.
- Storage conditions.
- Mixing or combining received batches (Resolved question 14).
