Use the [approved transfer plan](../plans/2026-11-18-transfer.md) for the feature contract and the [original handoff](2026-11-18-0827-transfer-feature-plan.md) for context. Address the review findings below as part of that implementation.

## Feature contract

An inventory member can permanently transfer a whole seed bag or a weighed portion to an opted-in organisation, including a testing provider. The first send in each direction reserves the selected bags until a recipient Admin accepts. Subsequent sends on that directional link complete immediately. Decline and sender cancel release the reservation and leave a split portion as its own bag. Bags out for testing are ineligible.

Completion creates a recipient-owned batch and bag, takes the moved weight out of sender inventory, and records the sender’s history. Recipients see the species, source collection code, transfer hops, latest result per test type with stats and performing organisation, and storage dates and durations. Keep the UI work in `apps/web`. Use forward-only Supabase migrations. The user applies schema changes and regenerates types.

## P1 findings to address first

### Commit enum additions before using them, and update ledger validation

Use an enum migration followed by a migration for dependent constraints and functions. PostgreSQL requires the `ALTER TYPE … ADD VALUE` transaction to commit before the value can be used in a constraint. Extend `batch_weight_adjustment_reference_shape` as planned and update `seed_transfer_event_reference_shape`, which currently rejects `ownership_transfer`. Update `validate_sub_batch_lineage_edge` to permit cross-owner edges for validated `transfer` events. Verify that the ledger item points to the source bag and that the completed transfer item maps to the destination bag and recipient. Preserve the owner and cycle checks for the existing lineage kinds. [PostgreSQL enum documentation](https://www.postgresql.org/docs/current/sql-altertype.html), [Ledger constraints](../../supabase/migrations/20260911000001_inventory_foundation.sql#L668), [Event constraint](../../supabase/migrations/20260911000001_inventory_foundation.sql#L788), [Lineage validator](../../supabase/migrations/20260911000003_inventory_operations_and_lineage.sql#L2406)

### Give each bag one active reservation and serialize request transitions

The proposed partial index on `ownership_transfer_item` cannot read the parent transfer’s status. Prefer a reservation table keyed by `sub_batch_id`, claimed and released in the same transaction as the transfer transition. An item-local release marker with a partial unique index is also viable. Enforce one open transfer request per directional org pair. Take the same pair lock in send, respond, and cancel before reading link or request state. Lock affected bags and then their batches in stable ID order. Check terminal state under those locks before creating a ledger event or releasing a reservation. Without the pair lock, an acceptance can finish before a concurrent send attaches to its request, leaving a bag reserved indefinitely. [Plan §§1.4 and 2.2–2.5](../plans/2026-11-18-transfer.md#1-schema-one-forward-migration), [PostgreSQL index predicates](https://www.postgresql.org/docs/current/sql-createindex.html), [Testing lock order](../../supabase/migrations/20260911000004_testing_work_and_custody.sql#L309)

### Close storage within the authorised completion path

`fn_set_sub_batch_storage` checks whether `auth.uid()` is a member of the bag’s current holder. A recipient Admin accepting a pending transfer fails this check while the sender holds the bag. Add a narrow internal close operation for an already validated transfer and locked bag, with a no-op for bags without an open storage period. Keep the public storage RPC’s holder check. The public RPC can remove a bag from storage with an `UPDATE` alone, so the proposed insert-only reservation triggers miss that path. Guard relevant updates and direct writes as well, checking the reservation under the same bag lock used to claim it. Audit the other bag mutation paths listed in §2.7. [Storage RPC](../../supabase/migrations/20260911000003_inventory_operations_and_lineage.sql#L1485), [Storage update policy](../../supabase/migrations/20260911000005_permissions_rls_and_integrations.sql#L1594), [Reservation scope](../plans/2026-11-18-transfer.md#27-locking-reserved-bags)

### Enforce recipient approval in SQL

Today a requester Admin can update an existing link. The validation trigger fires on insert and updates of `provider_org_id`, so changing a testing link’s `kind` could create a transfer link without recipient approval. Restrict direct authenticated writes on both link tables to testing rows, including both old and new rows on update. Route transfer writes through the authorised lifecycle RPCs and scope existing testing reads and writes to `kind = 'testing'`, including the edge functions. Revoke `EXECUTE` on the internal completion helper from `PUBLIC`, `anon`, and `authenticated`. Scope the existing `organisation_select` link clause to testing links, since transfer links would otherwise expose the sender’s organisation row and its contact fields. Return only the partner fields the transfer UI needs. [Link RLS](../../supabase/migrations/20260911000005_permissions_rls_and_integrations.sql#L2026), [Provider validation triggers](../../supabase/migrations/20260911000005_permissions_rls_and_integrations.sql#L2619), [Function grant defaults](../../supabase/migrations/20260911000005_permissions_rls_and_integrations.sql#L2713), [Organisation RLS](../../supabase/migrations/20260911000005_permissions_rls_and_integrations.sql#L2008)

### Verify provenance against completed transfers and limit the response fields

Authenticated inventory users currently have a table-level `UPDATE` grant on `batches` and can update their own rows. Protect `received_transfer_item_id` from client writes. In each provenance RPC, verify that the caller owns the batch and that a completed transfer item records this exact batch and bag as its received output. Apply the same validation when following onward hops. Project allowed result fields explicitly, since quality result JSON includes free-text notes. Use `result.test_type` for quality subtypes, filter `deleted_at IS NULL`, and rank by `tested_at DESC NULLS LAST` with a stable ID tie-breaker. Keep the plan’s batch-level test scope and its cleaning boundary. [Provenance plan](../plans/2026-11-18-transfer.md#26-read-functions-for-the-recipient), [Batch grants](../../supabase/migrations/20260911000005_permissions_rls_and_integrations.sql#L878), [Quality result shape](../../packages/common/types/index.ts#L181), [Soft-delete precedent](../../supabase/migrations/20261013000001_delete_quality_test.sql#L260)

**Product decision still open.** Confirm whether test results are captured at transfer completion or stay live. A live query would also show tests the sender later records on retained seed from the source batch. The review recommends capturing the allowed result fields at handoff. Continue the independent schema and write-path work while this is resolved.
